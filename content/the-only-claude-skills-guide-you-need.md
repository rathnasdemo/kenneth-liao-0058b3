> **TL;DR:** Skills fix a context engineering problem: loading every tool definition into the system prompt wastes tokens. A skill is a folder with a SKILL.md file, and only its name and description are loaded up front, which is progressive disclosure. Unlike slash commands the agent chooses when to use a skill, and unlike MCPs a skill is far simpler to set up. You can use skills in the Claude app and in Claude Code, and I show a cohort model skill and a YouTube thumbnail skill in action.

Today I am deep diving a new feature from Anthropic, Claude agent skills. I deliberately did not make this right away. I wanted to spend some time using skills, creating my own and testing them, so that I understood their purpose first.

I will break down what skills are, why they matter, how they differ from slash commands, MCPs and the rest of the current ecosystem, and how you can build your own and optimize them to solve real problems today. Whether you are technical or not, I will show you how to use skills in the Claude app as well as in Claude Code. Fun fact: the title and thumbnail for this video were generated by my personal assistant agent, using a custom skill that I built. At the end I bring it all together with a live demo of that assistant using the skill to solve a real problem of mine.

I also put together a cheat sheet of notes with the full comparison against MCPs, sub agents and so on, how to create custom skills and optimize them, and, most importantly, all of my sources. I will share it in the description. For fun, I fed the entire note to Claude and asked it to use the PowerPoint skill to generate a presentation. It is not bad, though the graphics could be better.

## The problem skills are trying to fix

*[Watch from 2:27](https://www.youtube.com/watch?v=421T2iWTQio&t=147s)*

The way things currently work, you typically load all tool schemas, whether they are local tools or from MCP servers, into the system prompt. We do that because we want the agent to have every capability: browse the web, scrape data, work with the local file system, run bash commands, and connect to MCPs for Google Drive, Calendar, Notion, Slack and so on. Until now you had to load all the directions and documentation for those capabilities up front.

That is very token inefficient. For the task at hand you might use only a few tools, say less than 10% of the tokens you loaded for all those tool definitions and usage instructions. So this is a context engineering problem, and it is the problem skills are trying to solve.

## What a skill is

*[Watch from 3:32](https://www.youtube.com/watch?v=421T2iWTQio&t=212s)*

Conceptually, skills are really simple. A skill is a folder. At a minimum it needs a SKILL.md file. Everything else is optional additional context: a scripts folder with Python or bash scripts the agent can run, markdown or text files with extra context, even data such as CSV files.

The SKILL.md file always has the same structure. First comes YAML front matter with a name and a description. The description matters a lot because, just like a tool description, it tells the agent what the skill is and when to use it. Then comes the body, which goes into detail and holds the instructions for actually using the skill to accomplish a task. That SKILL.md file is all you need.

## Progressive disclosure

*[Watch from 5:17](https://www.youtube.com/watch?v=421T2iWTQio&t=317s)*

The main design pattern, and what makes skills so powerful, is progressive disclosure. When you give a skill to an agent, the only thing loaded into the system prompt is the name and description, the front matter. If the agent decides to use the skill, it then reads the rest of the markdown body with the additional context and instructions.

That is token efficient, and it is what makes skills attractive compared to MCPs, where the context has to be fully loaded into the system prompt. It lets you fit far more functionality into an agent. For example, an MCP might have 20 tools that, with schemas and instructions, take up say 3,000 tokens in the system prompt. A skill giving the same functionality might initially load only 50 tokens, the name and description, with the rest loaded later as needed.

The idea is not new or exclusive to skills. It is just context engineering, and I and others use the same approach to progressively disclose context to agents like my personal assistant, which I built with the Claude agent SDK. We will see that in action when we build our own skill.

## Skills versus slash commands

*[Watch from 7:06](https://www.youtube.com/watch?v=421T2iWTQio&t=426s)*

I focus on slash commands and MCPs because they overlap most with skills. My notes compare skills to sub agents and projects too.

Slash commands are similar to skills in that they have a predefined prompt detailing a workflow for the agent. The main difference is that you trigger a slash command yourself, whereas a skill is used by the agent, which decides when. That lets skills be used more dynamically.

Imagine a slash command that takes input arguments besides the prompt. Instead of you doing the research to work out what to pass in, the agent chooses when to use the command and which arguments to use. It does that pre-work for you, calling whatever tools it needs and gathering context. So with skills you offload more from yourself to the agent and give it more autonomy.

## Skills versus MCPs

*[Watch from 8:34](https://www.youtube.com/watch?v=421T2iWTQio&t=514s)*

In terms of functionality, there is nothing you can do with skills that you cannot do with MCPs. MCPs have tools, but also resources, which are like the additional context or data in a skill, and prompts, which are like the SKILL.md file. There are two key differences.

- **Complexity.** A skill is much simpler to implement. You do not stand up MCP server infrastructure or MCP clients. It is markdown files, with scripts if you want.
- **Progressive disclosure.** Claude only sees the name and description at the start, so the context load is minimal.

On that second point I am honestly not sure why it is the case. Technically we do not have to do this with MCPs. We could tell Claude in the system prompt only which MCPs are connected, and when it wants to use one, progressively disclose its tools and tool docs as needed. I have done that with custom agents I built. I do not understand why this is not already implemented in Claude for MCPs, so if you have an idea why, let me know in the comments.

## Three benefits of skills

*[Watch from 10:22](https://www.youtube.com/watch?v=421T2iWTQio&t=622s)*

I think you get three key benefits.

1. **Context efficiency.** This one is huge. The Claude harness already takes care of how skills are used and the directions that go into the system prompt, so you get an efficient system for loading context out of the box.
2. **Simplicity with power.** It is ultimately markdown files with instructions, yet you can make skills more complex by adding tools, scripts and bash commands the agent can run.
3. **Compounding abilities.** Skills can leverage other existing skills. I have an Excel model builder that leverages the default Excel skill Anthropic developed, so you do not reinvent the wheel and can piece skills together into more powerful ones.

## Using skills in the Claude app

*[Watch from 11:47](https://www.youtube.com/watch?v=421T2iWTQio&t=707s)*

In the Claude app, desktop or web, it works the same way. Go to settings, then capabilities, and scroll to the very bottom, where there is a new section for skills. It comes with a bunch out of the box, developed by Anthropic. They start off, and you enable the ones you want.

Useful ones include the skill creator skill, which lets you prompt Claude to build a skill for you. That is basically vibe coding a new skill, and you can see the best practices Anthropic themselves coded. There are also skills for building MCPs and artifacts. You can upload your own too: you just upload a valid zip file of the skill folder. The SKILL.md must sit in the root of the folder, with the scripts directory next to it, and it must have valid YAML front matter with the name and description, otherwise the upload errors out.

## Demo: a cohort analysis skill

*[Watch from 13:56](https://www.youtube.com/watch?v=421T2iWTQio&t=836s)*

After uploading, I started a new chat and used my cohort analysis skill on a CSV of transactions data. A cohort model is a financial model that I build in Excel, and I gave the skill instructions for how. I simply told Claude to build a cohort model. There is a lot of context behind that ask, and it is all detailed in the skill file. Claude examined the file, recognized from context that it had a cohort analysis skill for exactly this kind of task, read it and started building.

It finished with a summary: almost 20,000 transactions in the data set, so not a small one. I opened the Excel file in Google Sheets. The gray columns are the raw data, exactly as the input CSV, and it added three columns and built the model in another tab. At the top is a table of input assumptions. Below are metrics laid out by cohort, grouping customers by their first transaction date, tracking things like retention rate over time, then customer counts, transaction counts, revenue, and eventually the lifetime value of the customer, LTV, and the CAC adjusted LTV.

Every cell in the model is formula based, and it is not easy to write formulas without errors. So the scripts folder has validation Python scripts, and the skill instructions tell the agent to run a validation script after inserting the formulas to make sure there are no formula errors. To check that it works, I changed an input parameter to 20 and then to 5%, and all the numbers updated live. As a finance manager for an analytics team at a fintech company, I can tell you this is an insane amount of work to do by hand, so being able to program it into a skill and have it be this reliable is amazing to me.

## Skills in Claude Code

*[Watch from 18:31](https://www.youtube.com/watch?v=421T2iWTQio&t=1111s)*

Skills work the same way in Claude Code, and also in any custom agent you build with the Claude agent SDK. In my personal assistant project there is a .claude folder where you normally load sub agents, commands and so on. You add a new folder called skills, with a folder for each skill. The cohort analysis skill there is the exact same one I zipped for the web app, which shows how portable skills are.

I also have the Excel skill Anthropic developed. They have a repo with all their default skills, linked in the notes in the description. Under document skills are the ones for working with PDFs, docs, PowerPoint and Excel files, and you can check out their anatomy there.

## Anatomy of my YouTube thumbnail skill

*[Watch from 19:55](https://www.youtube.com/watch?v=421T2iWTQio&t=1195s)*

My third skill creates YouTube thumbnails, and I want to walk through it so you can design a powerful skill yourself. The SKILL.md has a name and a very detailed description saying what the skill is and specifically when to use it, here whenever the user asks to create a thumbnail from scratch or edit an existing one.

At the top I list a table of contents for all the relevant context. For a complex skill that loads additional context, this matters because the agent needs an organized place to see where to go for specific information. Do not just list the files; describe at a high level what is in them, so the agent can decide whether it needs to read each one.

- **Required reading.** The design requirements are the same for every thumbnail, so the agent always reads them. It also always reads the prompting guidelines, because it uses Nano Banana, and I want it to read the best practices for prompting it every time. That is laid out as absolutely mandatory.
- **Optional assets.** Icons, a headshot of me and templates, all loaded only as needed. These locations are not even in the skill folder, so you can point to context elsewhere on your system.

The design requirements doc holds data I pulled from lessons I took on VidIQ for optimizing thumbnails. The templates file holds proven designs, and it is only loaded if the agent decides to create a thumbnail from a template rather than from scratch. That is progressive disclosure in practice.

## Context engineering in my personal assistant

*[Watch from 23:30](https://www.youtube.com/watch?v=421T2iWTQio&t=1410s)*

For the live demo, I want to show how progressive disclosure works in the personal assistant, since it is a context engineering problem. When the assistant starts, it loads the CLAUDE.md file in a context directory I created. It explains the subsystems for memory, projects and tools, each in its own subdirectory, and says the agent must read the CLAUDE.md at the root of each before doing anything else, to learn how that system works.

In the projects directory, the CLAUDE.md lists my projects with a brief description of each. The CLAUDE.md for my YouTube project lists a project overview file and a YouTube studio file, and the agent may click into the overview for specific details about my channel. I encourage you, whether working with Claude or building your own agents, to always think about the context engineering you put into the system. It is a skill worth building for maximizing context efficiency.

## Live demo: titles and thumbnails

*[Watch from 25:38](https://www.youtube.com/watch?v=421T2iWTQio&t=1538s)*

In my YouTube folder there is an episodes directory, where I created a research.md for the episode I am filming. All it has is the first five video results from searching Claude skills on YouTube. I pasted in a prompt asking Claude for title and thumbnail ideas for a video about Claude skills, pointing it at the research doc.

You can see the context system working: it checks its memories, looks at the projects CLAUDE.md, calls MCP tools from the YouTube analytics MCP for data on those videos, and runs curl commands to fetch the thumbnails. Claude is multimodal, so it can understand the thumbnails, and that matters because I want high click-through thumbnails and titles. It can look at existing thumbnails, understand their structure and apply those design patterns.

It came back with options. Option one was the unfair advantage angle, "Claude skills changed my workflow forever. Here's how." That is pretty clicky. Option two was the complete system angle, "The only Claude skills guide you need, from zero to expert". I like that one too. Others, like one that said no code is required, did not make sense since we dive into code. I asked it to add options one and two to the research doc and then create the thumbnails. Only then did it call the thumbnail skill, which holds the detail on how to write the prompt and apply the best practices. It looked at the templates, then called Gemini in a bash command. Claude Code can run terminal commands, so it invoked the Gemini CLI, which is already connected to the Nano Banana MCP server, and generated the thumbnails through Gemini.

## Improving a skill over time

*[Watch from 34:15](https://www.youtube.com/watch?v=421T2iWTQio&t=2055s)*

If you just create the skills directory in your .claude folder, it works with both Claude Code and any agents you build with the Claude agent SDK. One final tip: whether you create a skill with Claude's skill creator or by hand, there will be times it does not behave how you want. Like anything you vibe code, you improve it by prompting your agent.

What works for me is telling Claude Code or Cursor that the skill failed because of a given reason, showing it the expected output versus what happened, having it review the skill and identify the failure point, suggest how to improve it, and implement the fix. You iterate toward the output you expect.
